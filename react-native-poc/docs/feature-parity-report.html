02 What shipped, item by item

Real receipt rendering

Done

Replaced the Checkpoint-10 ASCII placeholder with a real Skia pipeline: offscreen raster surface, Paragraph-API RTL text (plain drawText doesn't reorder bidi text — the Paragraph API is the real equivalent of the PWA's ctx.direction = 'rtl'), IBM Plex Sans Arabic bundled and loaded via MakeFreeTypeFaceFromData, ZATCA QR generated client-side for offline printing, logo fetch-and-draw. Ported the PWA's exact 18-step layout algorithm line-for-line.

Disclosed limit

Whether Skia's on-device shaper actually joins Arabic glyphs correctly, and whether a real thermal printer's raster interpretation matches what was rendered, is unverifiable from this environment. Falls back to the old ASCII builder only if the real renderer throws — a safety net, not the intended path.

Printing configuration

Done

Ported DEVICE.printCustomerReceipt / printKitchenTicket / printReceiptLogo / kitchenPrinterIp / kitchenPrinterPort exactly, including the source's asymmetric defaults (customer receipt on, kitchen ticket off). Both enqueue call sites were previously unconditional — now gated on these real toggles before a job is ever queued, matching the PWA's own enqueue-time gate.

Refunds, void, cancellation

Done

Built a real manager-PIN modal (verify_pos_manager_pin) and used it to close a disclosed gap from Checkpoint 7: voiding a dine-in order called cancel_dine_in_order with no approval gate at all. Added an Order History screen (completed / cancelled / refunded tabs, detail view) wired to the existing refund_pos_order RPC.

Backend

Neither RPC needed a fix. refund_pos_order has never been rewritten since it was first written — idempotent by its own status = 'completed' guard. Both RPCs are gated only by pos:register server-side (any cashier's PIN qualifies) — the manager approval is a client-side compensating control, exactly matching the PWA's own, already-accepted design; not a new gap found here.

Loyalty — redemption

Done

Real two-device flow: cashier calls the production /api/pos/request-loyalty-redemption route, the customer confirms on their own phone's loyalty-card page, the cashier's screen polls loyalty_redemption_requests.status every 2s for up to 2 minutes, then shows the real redeemable-item list gated by the customer's actual points balance.

Bug fixed along the way

domain/order.ts's buildItems() hardcoded points_cost: 0 for every line item since Checkpoint 5. The backend's spend logic was already correct — it just never received a non-zero cost to deduct. Fixed to look the price up from the product's own points_redeem_price, matching the PWA's real lookup.

Loyalty — earning

Migration drafted, not deployed

A real production regression: complete_pos_order's 20260829200000_fix_pos_checkout_points_and_customer_id.sql rewrite kept points-redemption but silently dropped points-earning entirely — confirmed by reading its full body. No checkout path in production currently credits loyalty points on a sale.

Status

A minimal, idempotent restoration migration was written, committed for review, and sent to you — not applied to production. Awaiting your review and deployment confirmation before I can verify it against the live backend.

Barcode

Done

One combined search/scan TextInput now backs both plain name filtering and exact-barcode lookup on Enter — exactly how a USB/Bluetooth HID scanner behaves (types the code, sends Enter). A match routes through the same product-tap handler every grid tap already uses, so modifier-required items still open their picker. An unrecognized code shows the PWA's real "no product with this barcode" toast, gated to retail businesses only.

Bluetooth / USB printing

Architecture implemented, real APIs, hardware-untested

Per your explicit instruction to build the real transport now rather than defer: iOS gets CoreBluetooth (BLE) — the only Bluetooth path Apple allows a non-MFi-certified accessory. Android gets classic Bluetooth over the standard SPP UUID (the transport most real cheap ESC/POS printers actually use) plus real USB host mode, filtered by USB Printer Class rather than any vendor allowlist. Both request real OS permission/consent before ever opening a device. Wired into print and cash-drawer paths on both platforms, plus a real device-scan-and-select UI in Settings — never a free-text device-id field.

USB / Classic-BT on iOS

Not implemented — a genuine Apple platform restriction (ExternalAccessory/MFi-only), not an oversight. Reports TRANSPORT_NOT_SUPPORTED honestly rather than faking success.

Two real bugs found and fixed via CI, not claimed clean on the first try

  • The new iOS Swift file wasn't registered in the four places Xcode's .pbxproj requires for a non-filesystem-synced project — a build failure, not a runtime one, so it was loud and immediate.
  • The transport's error enum didn't declare conformance to Swift's Error protocol, required for use with Result<T, E>.

Both fixed and reverified — the HEAD commit is green on both platforms, confirmed by CI's own compiled-symbol check (it greps the build log/class output for each new file by name, not just "the build didn't error").

Customer management

Done (earlier this pass)

Search/select/create-new, reusing the PWA's real customer shape and search behavior — no new customer model invented.

Backend fix — deployment status unconfirmed

The same rewrite that dropped points-earning also dropped complete_pos_order's find-or-create-by-phone logic for a new checkout customer with no prior ID. A minimal restoration migration was drafted, approved by you with strict scoping, committed, and sent for manual application — I have not yet received confirmation that it's been applied, so the "new customer → one row created" behavior remains unverified against live production.
