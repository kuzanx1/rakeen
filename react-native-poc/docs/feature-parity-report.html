01 What this pass found and fixed

Six real bugs, found by a dedicated audit comparing every receipt and order-flow code path against the PWA's actual behavior, then verified and fixed. Two are compliance-relevant, not cosmetic.

Dine-in settlement receipts printed zero VAT and zero items

Fixed

handlePayDineInOrder hardcoded lines: [], discount: 0, vat: 0 on every dine-in tab close. That zero VAT amount also fed the ZATCA QR code — a real compliance bug for any VAT-registered business, not just a display issue. Now fetches the order's real, already-written subtotal/discount/VAT/total and real items (with mods/notes) via the same query Order History's detail view uses.

Kitchen tickets never printed for pickup/delivery

Fixed

Only dine-in registration ever enqueued a kitchen ticket. The PWA's real checkout flow prints one for every channel except a resumed dine-in tab close — pickup and delivery orders were silently getting no kitchen ticket at all, even with the toggle on.

Receipts could print item names in English

Fixed

Line-item names preferred the English name field when set. The PWA's real receipt/kitchen builders always use the primary Arabic name, regardless of the cashier's own UI language toggle — receipts are never printed in English.

Pickup/delivery receipts always showed "Order (offline)"

Fixed

The real, server-assigned order id was already coming back from the payment RPC and being silently discarded. Now surfaced through PaymentOutcome.orderId and used on the printed receipt whenever the sale synced immediately.

Order History showed "#123" instead of real product names

Fixed

Added a real name-lookup query (scoped to just the items on that one order, RLS-safe, no full catalog needed) — verified against the actual RLS policies on menu_items/services before shipping this, not assumed.

Order History had no reprint button

Fixed

A real, existing PWA capability that wasn't ported when this screen was first built this pass. Added, reusing the same real order data already fetched for the detail view.

App Store icon and permission blockers

Fixed

iOS's AppIcon set had zero actual image files (Contents.json listed sizes with no filenames — a real App Store Connect rejection). Android's launcher icon was still the stock React Native placeholder — a real Google Play rejection. Generated real icons for every required size on both platforms from the project's own existing Rakeen mark (public/pos-icon.svg), using a squared-off variant for iOS (which applies its own corner mask) and the real rounded design for Android. Also removed an empty, unused NSLocationWhenInUseUsageDescription — a blank usage-description string on a declared-but-unused permission is a real rejection reason.

Offline/queue/crash-recovery — no new bugs beyond one already fixed

Verified clean

A dedicated audit re-checked every new network call this pass introduced against the app's zero-connectivity requirement. One real bug was found and fixed earlier this session (a receipt-metadata fetch that could turn a successful offline sale into a false error) — the audit confirmed that fix is correct and complete, and found no other instance of the same pattern anywhere else in the loyalty, refund, cancellation, or drawer code.
